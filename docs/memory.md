# Project Memory --- COD Risk Intelligence & RTO Prevention

**Purpose:** Durable context for AI-assisted development. Read this file
before making substantial code or documentation changes.

## 1. Product identity

Project name: **COD Risk Intelligence & RTO Prevention Platform**

Assignment: Associate Software Engineer take-home, dated October 29,
2026.

Business: D2C haircare brand selling through Shopify. The product
evaluates each COD order before dispatch and recommends one of four
actions:

1.  `SHIP_AS_IS`
2.  `SHIP_AFTER_CONFIRMATION`
3.  `NUDGE_TO_PREPAID`
4.  `HOLD_CANCEL`

The product must balance Operations' RTO-cost concern with Marketing's
customer acquisition and conversion concern. Decisions must be justified
in rupees, not opinions.

## 2. Core product principles

-   Optimize expected business contribution, not accuracy alone.
-   Model predicts RTO probability; deterministic policy chooses action.
-   LLM interprets unstructured names/addresses; code handles
    arithmetic, validation, aggregation, thresholds, and state
    transitions.
-   First-time customers are not automatically risky or cancellable.
-   Sparse geography is unknown, not high risk.
-   LLM uncertainty/outage is not evidence of customer fraud.
-   High risk means hold/manual review in the MVP, not automatic
    cancellation.
-   Every decision has reason codes, plain-English explanation, model
    version, and policy version.
-   Dashboard separates observed actuals, estimates, and assumptions.
-   Historical replay must be point-in-time and leakage-safe.
-   Never invent dataset findings, model metrics, conversion rates, or
    savings.

₹402.38. - Initial prepaid discount hypothesis = ₹15.

These are supplied assumptions and derived estimates, not observed
performance of the system.

## 4. Dataset context

Uploaded file: `orders_sample.csv`, located in the conversation runtime
at `/mnt/data/orders_sample.csv` during initial analysis. It contains
approximately 2,018 rows and 17 columns, with records from April through
September 2026.

Previously observed exploratory notes: - One unresolved `IN_TRANSIT`
record was excluded from resolved-outcome RTO rate. - Initial raw
profiling identified duplicate order IDs and missing values; exact
counts must be regenerated by the implemented pipeline before being
cited in final memo. - Prior exploratory grouping suggested first-time
and returning customer outcomes differ, and regional variation exists.
Recalculate all counts/rates after deduplication and point-in-time
processing before using as findings. - Do not treat previously observed
aggregates as validated model features without checking leakage and
denominator definitions.

Expected fields include order ID/date, customer name/phone/address,
city/state/pincode, order value/items, prior order/RTO counts,
acquisition source, courier, payment method, and final status. Inspect
the actual CSV schema rather than assuming field names.

Target: - Delivered = 0 - RTO = 1 - Unresolved statuses excluded from
supervised training.

Never use `final_status` as a predictor. Never use future customer
history in a historical order's features.

## 7. Initial configurable risk bands

Starting defaults only; validate on chronological validation data:

-   0.00--\<0.20: low → ship as-is.
-   0.20--\<0.40: moderate → confirmation.
-   0.40--\<0.65: elevated → prepaid nudge if economics positive.
-   0.65--1.00: high → hold/manual review.

First-time status, LLM output, or geography alone must never trigger
cancellation.

## 8. WhatsApp and payment behavior

Confirmation: - Send immediately. - Explicit YES → confirm and release
to shipment queue. - Explicit NO → stop shipment and record decline. -
Ambiguous → ask for YES/NO; do not release. - No valid reply in 24 hours
→ hold/manual review, not automatic fraud/cancellation.

Prepaid: - Initial discount ₹15, configurable. - Show original price,
discount, payable amount. - Payment success → mark prepaid and
release. - Payment failure/decline/expiry → preserve original order and
use configured COD confirmation/manual review fallback. - Mock
transactions must be clearly identified as simulations.

## 9. Financial reporting rules

-   RTO expected direct cost: ₹169.40 under current assumptions.
-   Discount expense: actual redeemed discounts, not merely offers sent.
-   Genuine cancellation loss: estimated probability of delivery ×
    ₹402.38; label as opportunity cost, not realised cash loss.
-   CAC is generally already spent; do not double-count it as a new
    cancellation cost.
-   Net estimated impact = estimated avoided RTO cost − estimated lost
    gross contribution − redeemed discount cost − intervention cost −
    incremental operating cost.
-   Never count an avoided RTO twice.
-   Never treat all high-risk orders as avoided RTOs.
-   Do not claim causal intervention lift from observational historical
    data.

## 10. Model evaluation rules

-   Use chronological splits.
-   Keep September 2026 holdout untouched for final evaluation if data
    volume supports it.
-   Compute customer/geographic aggregates as of each order timestamp.
-   Fit imputers/encoders only on training data.
-   Compare baseline and candidate models.
-   Report precision, recall, F1, PR-AUC, ROC-AUC, calibration, and
    subgroup sample sizes.
-   Choose based on business cost and calibration, not accuracy alone.
-   Record split dates, eligible rows, class balance, and model version.

## 11. AI/LLM boundaries

Use LLM for: - Hinglish address interpretation. - Address
completeness/landmark extraction. - Ambiguous placeholder-name
assessment.

Use deterministic code for: - Phone/pincode format. - Exact placeholder
checks. - Duplicate detection. - Historical rates. - Financial
formulas. - Probability thresholds. - YES/NO matching. - State
transitions.

LLM output must be structured, schema-validated, and treated as a review
signal. LLM outage must not stop order evaluation.

## 12. Coding conventions and working rules
